# 用 gld 完成项目开发：能力与边界

## 结论

**gld 已能作为 AI 开发一个项目的主要工具入口，但还不能独立保证从需求到上线维护的
可靠、无人值守闭环。** AI 或操作者负责决策与推进，gld 提供本地执行与项目上下文；
测试、浏览器、Git 托管、部署系统各自负责其领域。能够运行它们，不等于 gld 已实现了
它们的验收、授权、恢复和审计语义。

CLI、库和常规后端项目，已有工具足以支持人工监督下的读改测审循环。Web、桌面和多机项目
还需明确补齐运行准备、界面/浏览器证据和环境验收。发布、数据库迁移、生产变更与权限
调整必须另有真实授权；不能因为用户让 AI “开发项目”就自动认为可以上线。

## 接入前先确认四层能力

| 层 | 要确认什么 | 不能代替什么 |
| --- | --- | --- |
| 源码 | 当前提交、工作树是否有改动、测试、Cargo.lock | 不证明正在运行的服务已经升级 |
| 构建 | 二进制版本、构建提交和实际链接的共享 crate 修订 | 相同版本号不代表相同代码；提交号也不包含未提交修改 |
| 服务 | `gld tool list --served`：正在跑的服务给客户端的工具表、指纹、构建提交；`check_exec_environment` 看策略 | 不能证明客户端拿到的就是这一份 |
| 客户端 | AI 调 `server_info`：`build_commit`、`connection.tools_fingerprint` 和上一行一致；再做一次无副作用调用看完整返回 | 不能用本机 CLI 成功替代远端连接验证 |

先列工作区，再为目标项目读取 `workspace_context` 和 Git 状态。不要根据上一轮对话猜
当前项目，也不要把工具数量当成覆盖率。本地 profile、服务实际给的表、远端工具和本机 MCP
转发工具是不同口径。

当前连接缺少工具或参数时，按 [troubleshooting.md 核对客户端拿到的工具表](troubleshooting.md#核对客户端拿到的工具表)
逐步查；2026-09-23 审查时那次就是客户端缓存了旧表。**不要编造参数、放宽权限或
使用解释器绕过策略**。`check_command` 不可见时也不能声称做过同路径预检。

## 生命周期覆盖

| 阶段 | 现在可用 | 还需谁负责 / 尚缺什么 |
| --- | --- | --- |
| 需求与范围 | 项目说明、Skills、Goal / Plan、可编辑文档 | 人或外部 AI 确认需求、约束、完成标准；没有需求自动验收器 |
| 架构与设计 | 跨文件阅读、搜索、Git 历史，编写 ADR / 契约 | 人或审查 agent 评估设计与依赖；不是已有语义索引或架构证明 |
| 初始化与依赖 | 运行获准的项目脚本、包管理器、编译器 | 工具链、锁文件、可复现环境由项目维护；没有统一任务发现与环境重建保证 |
| 编码与重构 | 补丁预检、文件读写、搜索、Notebook、Git diff | 版本前置条件需客户端支持并实际传入；不保护绕过 gld 的所有写者 |
| 本地运行与调试 | 命令会话、stdout / stderr、输入、取消；每条命令有运行记录（结局和最后 1～2 MiB 输出，gld 重启后读得到）；可连接获准的本机 MCP | 重启后不恢复进程、不重放；没有就绪探测或统一 dev-server 生命周期；真实 PTY 明确不做 |
| 测试与审查 | 调用项目测试、静态检查、构建；读取结果与图片；Task `finish` 收任务期间通过的命令作验收证据，并绑定当时的文件指纹 | 证据只证明"这条命令在这份内容上退出 0"，测没测到该测的由人判断；日志和报告要长期留存得另存文件 |
| 浏览器与界面验收 | 可组合已启用的浏览器 MCP 和项目 E2E 脚本 | 未完成跨项目绑定、就绪状态、console / network / trace / screenshot 的统一验收链 |
| 协作与 Git 托管 | Git 查询；获准命令可做本地 Git 操作；`gh` 显式放行后仅允许受限只读子命令 | PR 创建/合并、CI 重跑、Release 等写操作不能假设已获准，当前交给操作者 |
| 打包、发布与部署 | 项目脚本、外部 CI/CD、经 ccnm 操作登记过的远端项目 | 环境授权、变更审批、密钥隔离、产物签名与回滚演练不由通用执行工具自动提供 |
| 维护与交接 | History、Task、操作记录、再次读取当前仓库 | 没有独立调度/告警系统；历史文字不是可恢复进程、完整证据仓或不可篡改审计 |

## 当前可执行的工作闭环

### 先立完成标准，再开工

从项目自己的说明和构建入口出发，写清要改什么、不改什么、需要哪些验证及停止条件。
重大架构决策写项目 ADR，不把 gld 自身的维护指令强塞到被开发项目。需要规划门禁时使用
现有 Planning；使用 Task 是为了追踪，不是为了绕过权限或默认获得系统隔离。

### 小批修改，保留被测版本

读相关文件和 diff，使用补丁预检，再落盘。`git_diff.files` 每个文件一条，带真实状态
（added / deleted / renamed 带 `old_path` …）、是否二进制、是否 staged；diff 文本被
`max_bytes` 截断时这张清单仍然完整，以它为准数改了几个文件。
原生 API 的 `expected_versions` 可以降低
覆盖外部修改的风险，但它是可选的大小/修改时间令牌，不是内容哈希或强 CAS；客户端
未暴露它时要明确记录这一限制，重新读取上下文，不宣称已经使用该保护。

长命令在返回 `running` 后还没有完成；用 `read_output` 继续读到 `running: false`，
它会回 `termination_reason`、`exit_code`、`command_ok`。**不能只看工具的 `ok` 或 CLI
自身退出码**：命令退出 7 时工具 `ok` 仍是 true、`gld tool call` 仍退出 0，要看
`command_ok` / `exit_code`。Planning 台账（`planning_manage action=state` 的 `execution`）
按命令终态记：`failed` / `timed_out` / `cancelled` / `running` / `unknown`，`last_error` 写明退出码；
后台命令的终态在 `read_output` 读到时补回（gld 退出时停掉的 `interrupted` 记 `cancelled`，没来得及记
结局的记 `unknown`）。后台测试期间修改源文件会令证据归属不确定，
即使最后退出 0 也不作数——Task 验收会按 `workspace_writes_since_start` 和文件指纹拒收。

### 验收必须有证据

每项验收至少记录：目标与标准、被测版本、平台/工具链、实际命令、退出状态、关键输出、
证据位置、未执行项目及原因。测试全部通过、部分跳过、缺依赖直接返回、结果未知应分开。
截图证明界面外观，不证明控制台无错；服务启动成功也不等于业务就绪。

命令的结局和每个流最后 1～2 MiB 输出留在运行记录里，gld 重启后 `read_output` 照样读得到，
但每个项目只留最近 64 条、最长 7 天，输出不脱敏（规则见
[命令的输出能读多久](concepts.md#命令的输出能读多久stdin-怎么关)）；本机 MCP 大结果只是短期缓存。
需要交接的日志、报告与制品应存成项目选择的位置上的文件，敏感信息先脱敏。不要把 `session_id`
或 `output_ref` 当成永久证据链接。

### 收尾与交接如实写

复核最终 diff、测试覆盖和剩余风险，再更新文档、任务与历史。用了 Task 的，最后一步
跑测试，再 `task_manage action=finish evidence_session_ids=[那条命令的 session_id]`：
失败、没结束、之后又改过文件的证据会被拒收，全部作数才进 `completed`，规则见
[concepts.md 任务怎么收尾](concepts.md#任务怎么收尾带证据才算-completed)。
确认放弃正式验收才收成 `completed_unverified`；**不能把这个状态说成验证全过，
也不能反过来说完全没测过**。

`pause` 之后写入和执行会被拒（`TASK_PAUSED`），但它不停已经在跑的命令。任务结束前
检查自己启动的命令是否还在运行，明确由谁接管或正常停止；不要结束其他主体的进程。

### 遇到中断，不盲目重放

基线不符时用 `task_manage action=refresh_baseline` 先看变了哪些文件，判定谁改的；
属于这个任务的带 `accept_fingerprint` 和 `reason` 接纳，不属于的先恢复原样。不要手改
内部状态文件；它们坏了（报 `STORE_CORRUPT`）按 [任务数据坏了会怎样](concepts.md#任务数据坏了会怎样)
处理。输出过期、连接断开或远端 outcome unknown 时，先核对操作是否已经发生；
带副作用的发布、迁移、写文件调用不能自动重试。

gld 重启过（守护进程停了、升级、机器重启），之前的后台命令读出来是 `interrupted`（gld 退出时
停掉的）或 `unknown`（gld 没来得及记下结局，进程可能还在跑）：两种都没跑完或结局不明，先核对再
决定是否重跑，别把它们当成失败后可以放心重放。

远端 coding 会话与后台命令的寿命由 ccnm 控制，不是永久 Job。需要长期运行的服务由
目标环境的服务管理器负责，gld/ccnm 只做获准的操作与观测。详见
[远端项目](concepts.md)。

## 安全与协作的最低边界

服务自己的凭据可访问该服务内全部项目；只开部分项目用
[gld grant](concepts.md#只开几个项目gld-grant)。grant 管的是"能进哪几个项目"：同一个项目里的
Task、History、Planning 对开了它的几把凭据是共用的，只有命令输出按主体分开。
命令白名单和工作目录限制不是 OS 沙箱；不可信代码或生产环境需先设计账号、文件权限、
凭据与网络边界。

本机 MCP 是服务级扩展，能力取决于那个 server，不继承某个项目的文件边界或 Planning。
只启用真实需要且信任的来源；工具说明、skill 和外部结果都是可能包含注入指令的输入。
`confirm=true` 或 `readOnlyHint` 也不是用户真实授权的凭证。完整说明见
[security.md](security.md)。

## 后续完善不应越过的职责边界

任务验收、命令失败传播、基线恢复、客户端工具表核对、本机 MCP 结果保真、文档生成门禁、
`git_diff` 文件清单，以及任务存储的并发与损坏处理，已于 2026-09-23 补上（见
[审查记录的处理进展](reviews/2026-09-23-lifecycle-and-docs-audit.md#7-处理进展)）。
项目级授权（grant）已于 2026-09-24 补上（[RFC-0007](rfc/0007-scoped-grants.md)）。
之后才按真实项目需要补最小的项目任务发现、运行准备、日志/制品与浏览器证据适配。优先复用项目已有脚本和独立 provider，
不要为每种语言、测试框架或部署平台内建另一套调度系统。

gld 保持本地服务和工具入口；ccnm 保持远端执行身份与会话权威；toexec 只承接双方实际
共用的基础实现。不恢复已经退役的单项目 MCP 主入口，不重新立项已完成的 U0–U5 / G1–G3，
也不把明确不做的 PTY、模型主循环、完整 IDE 当成本轮缺陷。
