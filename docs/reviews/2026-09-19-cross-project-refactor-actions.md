## 3. hub 收敛前置条件，对应 L1；主评审 X03/X07

目标是内部统一的 workspace 执行资源所有者，多种薄传输/CLI 入口。当前 `ToolContext` 同时含 auth、提示词/profile 与 SessionStore，不可直接整个全局共享。

| 调整 | 必要验收 |
| --- | --- |
| 执行资源与主体/grant/视图分离 | 同项目多个入口使用同一资源所有者，但不能读其他主体的输出。 |
| 单项目 scoped view | workspace 枚举、context、工具、Job、output、artifact/history 全部按授权过滤；猜 ID 不能越权。 |
| 保留 audience 边界 | 旧单项目凭据不能自动升级成 hub 全权限凭据；无人使用的旧兼容路径核对后可以删除。 |
| 配置变更分类 | `context_fingerprint` 当前包含名称/instructions/skills，替换时会 terminate_all；改显示名不应杀任务，撤销权限不能仅改 UI。 |
| 资源身份与跨进程约束 | 目录别名、嵌套 root、独立进程/state home 不形成隐藏的第二写域；与 ccnm 同目录时先选一个执行权威。 |
| 停止语义拆分 | 关闭分享、撤销 grant、停任务、移除注册、关闭 hub 各有明确副作用。 |

达标后再把 README/CLI 默认路径收敛到 hub，并清理平行生命周期代码。显式隔离部署的单项目实例仍可保留，不要误删必要的资源管理命令。

## 4. 远端后台任务与能力协商，对应 L2/G1 后续；主评审 X04–X06

**优先复现组合问题**：`bridge/session.rs` 的 coding idle 是 120 秒，`Slot::is_idle` 看在途调用与最后使用时间，不知道已返回的远端后台进程是否仍活跃；ccnm 连接结束会停掉命令。启动后台任务后超过两分钟不调用，可能被回收。本轮只做源码组合推导，未运行长时复现。

不要只把 `wait_ms` 的 50 秒上限改大。它与单次调用 60 秒、租约 120 秒、任务运行期限和输出 TTL 是不同问题。近期明确租约显示、续租权限/预算、活跃 Job 的回收规则；远端现有 session-bound 行为不悄悄改成持久任务。

本地持久 Job 与远端状态投影分开：gld 可以记远端回执，进程终态仍以 ccnm 为准。断连是结果未知的候选，不能自动把写调用重开再跑。取消等待不应被未经说明地等同于取消命令。

`Offered` 已检查工具名和顶层参数名，继续保留，不重做 G1。补有实际需要的语义能力：嵌套 patch 操作、后台模式、stdin/TTY、等待/输出寿命与引用代次。Runtime 仍自行检查输入。不要升级成一个绕过白名单的任意 `call(name,args)`。

验收：超过空闲阈值的后台任务、超预算等待、断连重开、重复 stop、授权撤销、能力不支持、错误嵌套参数都有组合测试。任一拒绝发生在副作用之前，且不误作废有效句柄。没有实际 Runtime 证据时不宣称支持远端 durable Job。

### 落地注记（2026-09-20，`85bda77`）

**组合问题跑出来了**，用真实 gld 连真实 ccnm（`crates/core/tests/ccnm_background_lifecycle.rs`，没有 ccnm 二进制就跳过；本机跑法写在文件开头）。跑出来三条，前两条都比上面推导的 120 秒空闲回收**更早发作**：

| 查出来的 | 修成什么样 |
| --- | --- |
| 前台命令的期限比 hub 的调用预算还长：ccnm 不给 `timeout_ms` 就是 120 秒，hub 的预算是 60 秒，**默认值本身就打得爆它**。超时按"传输层不可信"丢连接，远端随即停掉这个会话的所有后台命令——出事的是前台那条，陪葬的是后台那些 | 前台命令在 hub 这边封顶 50 秒（`tools::MAX_FOREGROUND_TIMEOUT_MS`）：不给就填上，要更久就拒并指路 `run_in_background`。到点是远端杀命令并正常回话，连接和后台任务都还在 |
| 空闲回收看不见在跑的后台命令：`run_in_background` 的调用一返回就不是"在途调用"了，`Slot::is_idle` 那两道判断都看不见它 | 挂着后台命令时用 `CODING_IDLE_WITH_BACKGROUND`（10 分钟）。**不是"可以永远跑"**：写锁还占着别人的工作树，十分钟是个有尽头的数。计数只看请求、不解析远端文本，所以是上界，长阈值兜底 |
| **真实组合才查出来的**：连接被丢时会在远端留孤儿。`CLOSE_GRACE` 只有 5 秒，而 ccnm 读到 EOF 后要 TERM→2 秒→KILL 地停掉每条命令（够不着的等 10 秒才放弃）。机器忙时 5 秒不够，gld 就 `SIGKILL` 了 ccnm——它一旦被强杀，起的进程组没人收，那个 `sleep 60` 的 ppid 变成 1 留在远端，远端写锁的 `held` 标记也还在 | 宽限提到 20 秒（几乎从不用满），关连接不再占着槽位的锁做 |

顺带把两句话改准：会话没了时报的错明说后台命令跟着停了（`CodingError::NoSuchSession` 与 hub 的 `REMOTE_OUTCOME_UNKNOWN`）。原来模型只知道"句柄没用了"，会以为它起的构建还在远端跑——那正是 X04 说的"不能静默消失"。

**还没做的**：租约显示与续租预算（这轮只是把回收阈值改对，没有把租约摆到模型面前）；X06 的语义能力协商（嵌套 patch 操作、stdin/TTY、输出引用代次）；durable Job——那要 ccnm 升 `ccnm.workspace-mcp/2` 或显式协商，本轮连提都没提。ccnm 那半边的权威语义写在它的协议第 6 节（四个时钟、session-bound、取消等待不等于取消命令、终态只有 Runtime 说了算），本轮的修就是照着它做的。

### ccnm 那边同日又收紧了两处，gld 都不受影响（2026-09-20）

**写权不再被错误交出**（ccnm P43）：它的会话结束时若有命令停不掉，写锁留在 `held` 而不是标成可用，下一个 coding 会话被拒。对 gld 的意义是 `remote_coding_begin` 可能拿到一个新的拒绝理由——`workspace write guard was kept on purpose`，话里点名还剩哪些 `output_ref`。它和原来的 busy / unknown 一样是启动失败，`connect` 那条路已经把远端 stderr 带回来了，不用改代码。

**服务端开始自己验参数**（ccnm P44）：`exec_command`、`apply_patch`、`stop_command` 连同 `files[]` 的嵌套结构不再接受未声明的字段，超界的 `timeout_ms` / `preview_bytes` 从静默钳制改为拒绝。**gld 不受影响**，因为 `bridge::session::Offered` 本来就只转发远端 schema 里有的参数——这次收紧反而让那道检查有了依据：ccnm 的 `tools/list` 现在每个工具都发 `additionalProperties`，写工具是 `false`、只读是 `true`。

**可以顺手做、但这轮没做**：`Offered` 现在只比工具名和顶层参数名，可以改成也认 `additionalProperties`——远端说不收额外字段时，gld 这边多带一个参数就能提前拦住，而不是发出去等它拒。这属于 X06 那条「语义能力协商」的一小块，留着。
