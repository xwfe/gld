# RFC-0008：保持现有连接的连续升级

日期：2026-10-17，2026-10-30 按当前源码修订。状态：**稳定宿主基础实现中（§5），还没有零中断。**

现在的升级做法是换二进制 + `gld daemon restart`：服务断开零点几秒，在跑的命令被停掉，连接器、授权、地址都不动
（[安装 · 升级](../install.md#升级)）。本文讨论的是怎样连这点中断都没有：在跑的命令、在途请求、进行中的授权跨版本都不断。
承接 [RFC-0004](0004-one-service-many-projects.md) 的单 Hub 多项目架构；排队状态只在 [task_plan.md](../../task_plan.md) 维护，
实现和验证事实追加到[生命周期审查](../reviews/2026-09-23-lifecycle-and-docs-audit.md)。

写作时的源码基线是 `54bacbf` 加浏览器 grant 等改动（daemon 协议 6），在线构建是 `eea05359c42b`（0.8.3，协议 5）。

## 1. 结论与承诺边界

现有旧 daemon 不能通过当前接口完成严格零中断的首次代码切换。它同时拥有对外监听端口、Hub、tunnel、OAuth 的部分内存状态和运行中命令。当前重启先停止旧进程，再启动新进程；关闭流程主动终止 exec 会话。只保留配置与密钥、延长 graceful shutdown，均不能把这些资源转交给新进程。

所以现有版本之间的升级只能先停再起。要形成今后可持续使用的平滑升级能力，需要先在 gld 产品内部建立稳定宿主与可替换执行代的边界。无需用户安装或管理 Nginx、Caddy、Supergateway 等外部代理工具。

必须分别承诺两种升级：

1. **执行代更替**：稳定宿主不退出，新的工具实现就绪后逐步接管可交接的 workspace，旧请求和旧命令仍由其原来的执行代完成。完成本 RFC 的条件后，可以承诺此类升级不打断服务。
2. **稳定宿主本身升级**：涉及对外监听、隧道所有权、认证、单写者状态服务或宿主 IPC 的代码更替。它需要另外实现并验证宿主之间的资源与状态交接；在此之前，不能承诺此类升级零中断。把宿主改名为“内置代理”并不能消除这一边界。

当前 browser grant 修改涉及 HTTP 路由、认证及 daemon IPC。旧宿主尚无这些能力，不能把这次更新笼统归为已可热替换的工具 worker 更新。

## 2. 已验证的当前行为

| 资源/行为 | 当前所有者及源码证据 | 对升级的直接影响 |
|---|---|---|
| daemon 单实例与 IPC | `crates/daemon/src/lifecycle.rs`：`daemon.lock` 的跨进程排他锁；`server.rs`：进程内 App 与 IPC accept loop | 同一 `GLD_HOME` 不能直接并排启动两个普通 daemon；绕开锁不是交接协议 |
| restart | `crates/cli/src/commands/daemon.rs`：`Restart` 先看盘上运行记录，有命令在跑就不重启（`--force` 跳过），之后 `stop` 再 `start` | 不是滚动切换；原入口存在停服窗口 |
| Hub 的端口与 tunnel | `crates/core/src/hub/runtime.rs`：`HubRuntime` 持有监听任务、shutdown sender、Hub、work_session 启动检查、tunnel；`start` 先停止旧 runtime；`stop_runtime` 关闭监听、停止 tunnel、调用 Hub shutdown | 对外连接及隧道不独立于 daemon 存活；重启不能保持原连接 |
| 进程退出与命令 | `crates/core/src/app/runtime.rs`：`shutdown_all` 在停止服务前、后都调用 `terminate_all_sessions_everywhere`，中间还 `agents::interrupt_all` 停委派的 Agent | 正常退出也会终止运行中命令和 Agent；不只是 `--force` 才有影响 |
| graceful shutdown | `crates/core/src/runtime/port.rs`：监听任务等待约 3 秒，超时后 `abort` | 只是有截止时间的退出等待，不能证明长请求完整结束 |
| Hub 内部连接 | `crates/core/src/hub/mod.rs`：`Hub::shutdown` 终止 Hub scope 会话，并关闭 ccnm 远端连接、原生节点连接及 machine relay | 等待 HTTP 监听退出不足以保持其他 Hub 会话 |
| MCP 工具请求 | `crates/core/src/mcp/listener.rs`：请求通过 `spawn_blocking` 调用 endpoint；Actions 监听器（`actions/listener.rs`）、`gld tool call`（`dispatch.rs` → `App::call_tool`）是另外两条进同一批工具的入口；没有升级用的在途请求登记及 admission gate | 不能从服务数量或完成后的 usage 统计推断“可安全切换”；响应断开也不证明工具未产生副作用 |
| OAuth 身份 | `crates/core/src/auth/oauth_flow.rs` 与 `client_registry.rs`：签名 secret、client registry 等可持久化；授权码 pending map 是 OAuthRuntime 内存状态 | 复用密钥有利于保留已签发 token，但进行中的授权流程仍可能丢失 |
| 原生节点 | `crates/core/src/nodes/registry.rs`：`Nodes` 持有每台机器唯一的一条 WSS；连接从 Hub 监听器的 `/nodes/v1/connect/{machine_id}`（或全局入口）进来，`Hub` 经 `nodes.call` 转发 | 连接挂在公网入口上，不能跟着执行代走；换代断连接等于每台机器都要重连 |
| 委派的 Agent | `crates/core/src/agents/run.rs`：`LIVE` 表和子进程都在起它的进程里，`agent_manage start` 和 `gld agent approve/stop` 都能起或停；任务记录和 owner 锁在盘上 | 属于工作区执行状态；停和放行必须到起它的进程里做，看记录不用 |
| 通用任务空间 | `crates/core/src/hub/work_sessions.rs` 与 `managed_workspaces/`：登记在数据目录自己的存储里，不走 `DataStore`；启动检查由 `HubRuntime` 拉起，碰 `workspace_runtime` | 跟执行状态走，不跟监听器走 |
| exec 会话 | `crates/core/src/tools/session.rs`：ExecSession 持有进程 Child、ChildStdin、输出 reader task、内存状态；run record 另行落盘 | 持久化日志不等于接管进程和 stdin；重启后读取历史不能算命令连续运行与交互能力保留 |
| workspace 执行状态 | `crates/core/src/tools/workspace_runtime.rs`：SessionStore、workspace 写入序号与运行归属均在进程内；文件写锁通过同一 `GLD_HOME` 下的 fs2 锁协调 | 只把 session ID 路由回旧代仍不足够；新旧代并行写同一 workspace 会漏记对方的写入序号 |
| 配置存储 | `crates/core/src/data/store.rs`：整个数据文件读改写以进程内 Mutex 串行；正常架构依赖单 daemon 单写者。工具路径（`tools/`、`hub/`、`agents/`、`managed_workspaces/`、`machine_mcp/`、`bridge/`）现在只读不写它，写入都在 `App`、`nodes::config`、`nodes::pairing`、`secret/`、`global_gateway.rs` | 两代普通 App 共同写配置可能覆盖彼此修改；不能只取消 daemon 单实例锁 |
| 现有 global gateway | `crates/core/src/global_gateway.rs`：有流式 HTTP 转发实现，但其 runtime 和 tunnel 也归同一 daemon，且被 `App::shutdown_all` 停止 | 转发代码可以复用；现有生命周期本身不提供升级隔离 |

另一个容易误用的接口是 SIGHUP：当前 `server.rs` 将其作为退出信号处理，没有原地热加载含义（节点进程 `nodes/client.rs` 也一样）。`restore_runtime_state` 只根据保存的配置重新启动服务，不恢复原进程的连接、授权 pending map、stdin 管道或运行时任务。

## 3. 最小可落地的运行时所有权方案

采用 **gld 稳定宿主 + gld 执行代子进程**。这是同一产品内部的进程边界；安装、启动、状态查看仍由 gld 管理。执行代来自保留完整版本身份的二进制文件，通过仅本机宿主可访问的私有 IPC 通道通信。不能将执行代直接暴露为第二个公网入口。

### 3.1 稳定宿主持有的资源

宿主负责对外端口与已接入 HTTP 连接、现有 tunnel 进程和公开 URL、认证与 OAuth 流程、client registry、配置及授权的唯一写入入口、执行代路由与升级协调。在工具执行代更替期间，这些资源均不重建。

宿主完成每次请求的正常鉴权，把明确的 caller、grant、workspace 和只读范围传给选定执行代。执行代只接受可信内部通道传来的上下文；不能让客户端通过伪造转发头取得内部身份。撤销授权、Origin 校验和 workspace 限制仍走正常路径，升级不能引入临时无鉴权窗口。

认证代码放在宿主意味着认证功能变更属于宿主升级。这是有意收窄的第一版边界：它使执行代更替时已发 token、refresh token、注册 client 以及正在进行的授权码流程都有稳定的所有者。后续若要热替换认证实现，应先定义独立的状态接口和兼容性约束。

配置和 client registry 必须保持单写者。执行代通过宿主请求配置变更，不能各自加载整份旧快照后写回共享文件。此处不建议为了滚动升级顺便引入数据库；明确保留单写者即可。

### 3.2 请求与命令的所有者

每个已接受的工具请求绑定一个执行代直到完成；不能在执行过程中转交，也不能在不确定结果时自动重试可能产生副作用的调用。JSON-RPC request ID 本身不是跨重启的幂等保证。

第一版将 **整个 workspace 的执行所有权** 固定在一个执行代。它同时拥有该 workspace 的工具上下文、运行中命令、stdin/stdout、写入序号和执行证据状态。所有调用者访问同一个 canonical workspace 时，均通过同一个所有者，caller/grant 仍在其内部隔离。

不能采用“旧 session 回旧 worker，其余工具调用立即进新 worker”的简化。当前 workspace 写入序号是进程内原子计数：新代写入文件后，旧代可能不知道发生了新写入，从而错误评价旧测试结果与当前代码的一致性。跨进程文件锁只能串行部分写操作，不能修复这个状态遗漏。换一个 `GLD_HOME` 还会分离文件锁域，风险更大。

交接 workspace 前，需要在宿主的所有权锁下验证：原执行代没有该 workspace 的在途调用、运行中命令、未排空输出或未提交的运行记录；必要状态已完成可验证交接。之后再原子更新所有者。这个判断与切换必须是同一个受保护过程，不能“检查为空，过一会儿再切换”。历史 session ID 与输出仍须可查询；跨代验收证据必须保持原有校验语义，不能默默把无法证明的新鲜度视为有效。

长期运行的开发服务器会使其 workspace 继续使用旧执行代。允许旧代持续存活是不中断命令的代价。达到允许保留的代数或资源上限时，拒绝继续激活新的代，而不是为了完成升级而杀掉旧命令。如果产品要求这类 workspace 也立即获得新工具实现，下一阶段应把 SessionStore、子进程/管道和写入序号提取为稳定执行服务；这比第一版 workspace 固定归属涉及更大改造，不宜隐含在“加一层反代”中。

### 3.3 执行代升级流程

1. 暂存候选二进制到独立版本路径，保留当前版本；构建或下载完成不触发在线服务退出。
2. 宿主启动私有候选执行代，验证构建身份、兼容协议、状态格式及必要工具能力。当前 `wait_until_answering` 把任意 HTTP 状态视为入口有响应，不能直接用作升级就绪标准。
3. 候选就绪后，新 workspace 可使用新代；已有 workspace 只有在满足交接条件时转移。工具发现与实际执行能力需要按当前所有者保持一致，不能先发布新工具目录却把请求送给不会处理的旧代。
4. 已接入的调用保持原执行代，执行中的命令保持原 session ID、进程与管道。宿主对外入口和 tunnel 全程保持不变。
5. 旧执行代没有在途调用、活动命令、所属 workspace 或未完成状态交接后，才允许退出。升级等待超时仅报告“尚有旧代运行”，不能走当前三秒超时后 abort 的路径。
6. 候选失败时，在未产生新状态迁移的范围内保留或恢复原路由。回退代码不撤销已经执行的工具副作用；持久化格式不兼容时必须在激活前拒绝，而不能依靠回退补救。

可复用 `global_gateway.rs` 的请求和响应流转发代码，但必须将它的监听及 tunnel 生命周期移出会被替换的执行代。仅原样保留当前 `App::shutdown_all` 调用关系无法达到上述效果。

### 3.4 第一版怎么落地（2026-10-30 按当前源码定的）

本节写实现上定下来的做法，上面三节仍是设计依据。这里“执行代”的代码在 `crates/core/src/generation/`。

**进程关系。**`gld daemon run` 这个进程就是宿主，它起一个子进程 `gld daemon generation`（隐藏子命令，不给人直接敲）当执行代。

**私有通道是子进程的 stdin/stdout 这对匿名管道，一行一条 JSON。**不开 socket、不开端口，不进文件系统，所以没有第二个入口，也没有路径可以让客户端或项目命令连上来。执行代一启动就把这对管道 `dup` 成带 close-on-exec 的新描述符，再把 0 指向 `/dev/null`、1 指向 stderr：项目命令继承不到它们，哪段代码误 `println!` 也不会写进通道。Windows 上用 `stop_std_handles_being_inherited` 关继承（没有真机验证）。代价是通道不能交接：宿主一退，执行代就读到 EOF，按正常退出收掉命令后自己退。“稳定宿主更替”那一期要换成可重新连接的通道，这是已知的债。

**身份只来自宿主。**宿主验完鉴权，把 caller（principal、scope、grant 含 browser 标记）作为通道上的字段发给执行代。这些字段由宿主从 `AuthContext` 生成，不从 HTTP 请求里读任何东西，客户端写什么请求头或 JSON 字段都影响不到。

**谁持有什么：**

| 宿主 | 执行代 |
|---|---|
| 对外监听（Hub、单项目 MCP、Actions、全局入口）、隧道、OAuth 与 client registry、原生节点 WSS、配置与密钥的写入、`gld` 的 IPC socket | `ToolContext`、`SessionStore` 与命令进程、写入序号、委派的 Agent、ccnm 远端连接、本机 MCP 转发、work_session 启动检查 |

- **原生节点连接归宿主。**WSS 从公网入口进来，换代时断开就等于每台机器都要重连。执行代要调节点时经通道反过来问宿主（列成员、转发一次调用）。节点上的命令在节点进程里，不属于这边任何一代。`nodes/` 内部逻辑没动，只把 `Hub` 对 `Nodes` 的两处调用接到一个小接口上。节点进程 `gld node run` 自己仍是单体，升级节点仍是重启它，不在本期范围。
- **配置单写者靠硬约束。**执行代启动时关掉本进程的 `DataStore` 写入，写就返回错误；工具路径本来就不写，这是防以后有人不小心加上。
- **Planning 的状态文件不算执行状态。**`gld` 的 plan/goal 操作本来就按文件协调（直连模式也这么走），留在宿主；只有切 plan 模式时“停掉工作区里的命令”这一步发给执行代。
- **工作区所有权。**键是规范化后的项目根目录（远端成员、work_session 用各自的 id）。第一次调用把它绑到当前执行代，之后一直走那一代。判断所有权和计数在同一把锁里，切换也拿这把锁，所以不存在“查完是空的、切的时候已经有新请求”的窗口。
- **在途计数是实数。**请求进入执行代前加一、拿到回包才减一，客户端中途断开不减。按代和按工作区各记一份。
- **发现类请求（`initialize`、`tools/list`）走最老的那一代。**这样不会先发布新工具，再把调用送给不认识它的旧代。准备新代时要求它的工具表包含当前代的全部工具，少一个就拒绝。

**用户怎么操作。**`gld start`、`gld daemon restart` 照旧。多了四条：`gld daemon upgrade status`（只读）、`prepare <二进制路径>`（起新代、验证，不动路由）、`switch`（切过去）、`abort`（放弃新代）。`prepare` 不复制二进制，直接从给的路径起，所以路径要是一份版本化的副本（比如 `~/.local/opt/gld-<版本>/gld`）。

**执行代挂了怎么办。**宿主留在原端口。正在执行的请求收到 JSON-RPC 错误 `generation_lost`，说明结果未知、不会自动重放；宿主退避重启一个新执行代，配置和认证都不受影响。挂掉的那代起的命令成孤儿（和现在 `kill -9` 守护进程一样），记录判成 `unknown`。

## 4. 旧 0.8.3 的首次迁移硬限制

在线旧构建 `eea0535` 是单体 daemon。在当前 macOS 运行方式下，它没有预先提供监听句柄交接、存量请求登记与交接、tunnel 接管、OAuth pending 导出、exec 子进程与 stdin 管道移交协议。新二进制无法单方面补上旧进程未实现的交接能力。

因此，本次第一次引入稳定宿主时，以下表述都不成立：

- “先起新 daemon 再杀旧 daemon就能保持原端口”：同一数据目录的实例锁阻止普通双 daemon；即便绕过锁，旧监听仍占据原入口，配置也不具备双写安全性。
- “先等请求结束再重启就是零停机”：停止与重新绑定之间仍有入口窗口，且等待后仍可有新请求到来；没有入口所有者和 admission 协调便不能作此保证。
- “恢复配置和 token 就保持了会话”：这只覆盖持久化身份的一部分，无法保持旧进程内的授权事务、请求、命令控制管道。
- “隧道域名相同便不会中断”：域名复用不代表同一 tunnel 进程、TCP 连接或请求连续；临时 tunnel 重新启动还可能得到不同 URL。

**严格要求一次都不能断，就只能不升级。** 2026-10-17 用户选择在没有命令在跑时按现有做法重启升级（审查 §25），浏览器授权入口随之生效。

首次迁移若之后获得明确维护窗口，可以先让现有授权流程、请求和命令自然结束，保留原数据目录、身份与已配置公开地址，再启动新架构。这里仍应如实注明短暂入口中断及临时 tunnel URL 变化的可能性。这是旧版本能力边界，不是多加一次确认便能变成零中断的操作。本 RFC 不授权执行该迁移。

## 5. 分期实现

### 本次最小必要保护

保留“新 CLI 与旧 daemon 版本/协议不兼容就拒绝操作”的行为，不新增自动重启。提示照旧告诉用户换完二进制要 `gld daemon restart`，
并说明会断开片刻、停掉在跑的命令：交接机制做出来之前这就是升级的唯一做法，提示不能只说“别重启”而不给出路。

本次不建议额外增加只读“升级安全”CLI 命令。旧 daemon 只能提供服务数等粗粒度信息，没有在途请求、活动 exec、pending OAuth、资源所有权或交接能力的可靠快照。服务数为零也不能证明可安全升级；新命令若仅重复版本不匹配，会增加接口与文档负担，却无法建立新的安全保证。现有版本检查配合诚实提示已足以拒绝本次不兼容操作。

若未来开发安装器或升级激活入口，它必须把“暂存”与“激活”分开，并在任何关闭信号、端口回收或配置迁移之前检查在线版本能力。未知或缺失交接能力时拒绝激活，不能先破坏在线状态再发现无法继续。

OAuth 注册表的本轮必要修复是：同一实例内持锁保存成功才发布内存和 HTTP 201；满额拒绝新增而保留旧 ID；
既有文件读取或解析失败时保留原件、停用新注册，保存失败返回 503。磁盘重载测试验证旧 client_id、access 和 refresh，
不改变签名、授权范围或撤销规则；不代表跨进程写入、断电耐久性或旧记录恢复。
这项修复随 2026-10-17 的本机升级上线（审查 §25）。

### 下一阶段：稳定宿主基础

定义宿主和执行代 IPC、构建身份及兼容范围；迁出入口/tunnel/认证/单写者状态所有权；实现真实的请求计数、workspace 所有权和执行代状态。此时可以增加只读的升级能力/状态报告，用于解释哪个 workspace 仍留在旧代、等待的资源是什么。报告只含计数和标识，不输出 secret、token URL 或工具参数。

同时完成候选启动、严格就绪验证、可中止的激活流程和不破坏在线状态的失败处理。首次上线此架构仍受上一节限制。

### 再下一阶段：执行代连续更替

实现受保护的 workspace 交接、历史输出可查询、状态格式兼容检查和旧代保留机制。用真实长请求与交互命令验证，不以单个健康检查请求成功作为通过标准。

### 完整升级必须完成：稳定宿主更替

执行代更替通过仅是分期验收，不能关闭“每次升级都无中断”的要求。还必须设计旧宿主与新宿主之间的监听资源、已接入连接、tunnel、认证事务及单写者身份交接。需要旧宿主预先配合，按支持的平台验证，不能把新功能 worker 的通过结果外推到宿主更新。宿主交接协议未实现或不兼容的版本组合，保持旧宿主服务并拒绝无中断激活。

## 6. 零中断验收条件

| 场景 | 必须观察到的结果 |
|---|---|
| 持续 connector 请求覆盖切换前后 | 相同公开地址与认证身份有效；升级未产生连接重置、升级导致的 401/502/503 或客户端超时；延迟在约定预算内 |
| 切换时有长工具请求 | 原请求完成并收到原响应；不通过重放实现“最终成功” |
| 切换时有带副作用的调用 | 副作用仅执行一次，响应与调用对应；候选失败不自动再次执行 |
| 切换时有交互 exec | session ID 不变，原子进程继续运行；后续 stdin、增量 stdout/stderr 和退出码可获得 |
| 同一 workspace 有活动命令和新写入 | 调用归属一致；写入序号及测试新鲜度判断仍正确，不因分代漏记写入 |
| OAuth 流程覆盖切换 | 已有 access/refresh token、client 身份有效；切换前发起的授权码流程仍能完成；密钥未重新生成 |
| tunnel 与入口连续性 | 执行代升级前后宿主监听所有权、tunnel 进程及公开 URL 不变；不靠客户端重新绑定入口补救 |
| 候选启动失败、协议不兼容或状态格式不兼容 | 激活失败发生在修改在线路由/关闭资源之前；旧服务继续正常响应 |
| 长期运行命令阻止回收 | 旧代保留并清晰报告；等待超时及代数上限均不触发强杀 |
| 旧 protocol 5 首次激活 | 能力未知/不支持时提前拒绝，无 Shutdown、无端口回收、无配置迁移、无 exec 中断 |
| 稳定宿主升级 | 独立验证其交接协议；执行代更替测试通过不能替代这一项 |

验收中的“零中断”针对升级操作造成的中断，不声称能消除机器断电、网络失效或隧道提供方故障。检查与激活应在同一个所有权协议内执行；单纯先读取一个“当前空闲”快照不是验收依据。

## 7. 参考

- [MCP 2025-06-18 传输规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)：Streamable HTTP 的请求、响应与会话语义；采用 HTTP 不自动提供进程升级或工具执行幂等性。
- [nginx 进程控制与在线二进制更替](https://nginx.org/en/docs/control.html)：旧代继续服务既有客户端、候选失败保留旧代的进程生命周期参考。gld 方案由自身实现，不要求用户安装 nginx，也不把 nginx 的能力当成 gld 已有能力。
- [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591.html)：动态客户端注册与注册响应；客户端持有的注册身份应与服务端已确认状态一致。
