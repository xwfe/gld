# RFC-0007：给一把凭据只开几个项目（审查 D07）

日期：2026-09-24。状态：**已实施**（本机服务未升级，ChatGPT 上未实测，见 §6）。来源：[2026-09-23 审查](../reviews/2026-09-23-lifecycle-and-docs-audit.md) D07、
[RFC-0004 §4](0004-one-service-many-projects.md#4-代价和跨仓评审-x07-的关系) 留下的缺口。

## 1. 要解决什么

服务的凭据管它的**全部**项目：拿到口令或 bearer 令牌的人，连上来调一次 `list_workspaces` 就看到全部，
每个都能读、能写、能跑命令。本机那台服务就是 7 个项目挂在同一个公网地址上。想给别人（或另一个
客户端）只开其中一两个、或者只让看不让动，现在做不到，只能别把那几个项目加进来。

## 2. 怎么用

```bash
gld grant add alice api web            # 只开 api、web，只读：看得到、搜得到，改不了、跑不了命令
gld grant add me-laptop api --write    # 能写能跑命令：等于全权，只给你信得过的
gld grant ls                           # 有哪些、各开了什么（--reveal 显示口令和令牌）
gld grant rm alice                     # 立即作废
```

客户端那边地址不变：OAuth 的在授权页填这把的口令（不是服务口令），bearer 的用这把的令牌。

## 3. 决定和理由

**范围绑在凭据上，不绑在 client_id 上。** OAuth 这边任何知道口令的人都能自己动态注册一个客户端，
`client_id` 事先不知道；按它配范围，就只能"新客户端先全放开，操作员事后收紧"，中间那段谁都能进全部
项目。所以每个 grant 自带一把口令（给 OAuth 授权页）和一个令牌（给 bearer），用哪把进来就是哪个范围。

**现有凭据照旧是全权。** 服务口令、服务的 bearer 令牌，以及升级前发出去的所有 OAuth 令牌，都不带
grant，行为和以前一模一样：ChatGPT 连接器不用动。新发的全权令牌格式也和以前一样（不写这一格）。

**范围只有两样：哪几个项目，只读还是能写。默认只读。** 能写的 grant 能跑命令，命令能以你的身份读到
数据目录里的服务口令——命令白名单里有 python，挡不住（独立审查实测）。所以能写的 grant 挡不住存心的人，
只是把能碰的项目收窄给信得过的客户端；给别人的只能是只读的，于是默认只读、`--write` 要显式写。

只读按 `read-only` 工具集取交集（服务、项目自己的工具集照样生效，三者取最窄）。**远端成员只给读的那几个
远端工具，能写的 grant 也一样**：一个远端成员同一时刻只有一条写连接，换个主体开就把原来那条顶掉，grant
开一个就断了操作员正开着的会话和后台命令。**本机 MCP 转发（`call_mcp_tool` 那三个）grant 一律不给**：
它们是服务级的，能做什么由那个 server 决定，不属于任何项目。**关了 `confine-reads` 的项目不给 grant 用**：
那样读工具能读到项目外面。按工具、按路径细分不做。

**Git 工具只看项目那个子目录。** 项目是某个仓库的子目录时（monorepo 里的 api/），git 默认看整个仓库，
开给 api 的只读 grant 能用 `git_show HEAD:web/.env` 读 web。这本来就违反"读 Git 历史：项目目录内"，
所以对所有凭据一起修：默认补 `-- .`，拒绝 `:` 开头的 pathspec 魔法和指到项目外的 `提交:路径`。

**看不见等于不存在。** 范围外的项目不出现在 `list_workspaces`、`initialize` 的说明、任何报错的候选
列表里；按名字或 id 去调，报的是 `WORKSPACE_NOT_IN_HUB`，和根本没有这个项目一样。不然一次报错就把
其他项目的名字漏出去了。

**撤销在下一次请求生效，不用重启。** 令牌里写 grant 的随机 id（不是名字：删了再建一个同名的，旧令牌
也不会复活），验令牌时查这个 id 还在不在，不在就 401；刷新令牌也换不来新的。`gld grant rm` 的同时
停掉这把凭据起的命令会话，35 秒后再清一次：撤销前已经过了鉴权的调用可能正排在写锁上（最多等 30 秒），
它起的命令落在第一次清理之后。正在执行的那一次调用照常跑完——没有办法安全地打断一个写到一半的补丁。

**回滚到旧版本不能让 grant 变全权。** 旧版本不认令牌里的 `grant`、会把它忽略掉；grant 的令牌因此把
`token_use` 写成 `grant_access` / `grant_refresh`，旧版本只认 `access` / `refresh`，回滚后它们直接 401。

**改范围 = 删了重建。** 第一版不做"原地收窄"：收窄要按项目停它在被收走的项目里起的命令，删掉重建
一步就做到了，代价是客户端要重新授权一次。放宽也一样重建，保持一条路。

**同一个项目里不再往下分。** 两把凭据都开了 api，api 的 Task、History、Planning 两边都看得到、都能改：
这些是项目的记录，不是某个客户端的。命令会话本来就按主体分（[caller.rs](../../crates/core/src/tools/caller.rs)），
这一条不变。

**noauth 下不给建，有 grant 时也不给改成 noauth。** 没有鉴权就没有"用哪把进来"，谁连上都是全权。

**GPT Actions 不动。** 它本来就是一个项目一套凭据。

## 4. 不做

- 用户目录、自然人身份：grant 是"一把钥匙开哪几扇门"，不是"这是谁"。
- 审批队列、按工具 / 路径的细粒度授权、有效期（到期自动作废）。
- 原地修改范围（见上）。

## 5. 验收

| 场景 | 要看到的 |
| --- | --- |
| 服务口令、服务 bearer 令牌、升级前的旧令牌 | 全部项目，行为不变 |
| grant 的 OAuth 令牌 / bearer 令牌 | `list_workspaces`、`initialize` 只有授权的项目；调范围外的报 `WORKSPACE_NOT_IN_HUB`，候选里没有它；工具表里没有本机 MCP 转发 |
| 只读 grant | `exec_command`、`apply_patch` 这类被拒，`read_file`、`git_diff` 正常；工具表按只读列 |
| `gld grant rm` | 下一次请求 401；刷新令牌换不来新令牌；它起的后台命令被停掉；同名重建后旧令牌仍然 401 |
| 两把 grant 开同一个项目 | 各自的命令会话互相看不见 |
| 真实二进制 | 隔离数据目录里走一遍真的 OAuth 授权页（填 grant 口令）和 bearer，结果同上 |
